# YouTube recommendations — Research notes

Date: 2026-11-04. Companion to [the design](2026-11-04-youtube-recommendations-design.md).

How this was found: reading the code, changelogs and issue trackers of the open-source apps that use YouTube's TV sign-in, plus four anonymous requests from this Mac (youtube.com/tv and its script, one TV browse, one TV player, one TV next). Every load-bearing fact was re-checked against the sources by a second reader. **Nothing signed in was tried**, so every request shape below is provisional until Phase 0.

Licences: YouTube.js (MIT), SmartTube and its engine MediaServiceCore (MIT), yt-dlp (Unlicense). Smart Tube BDP (GPL-3.0), the Kodi YouTube add-on (GPL-2.0-only), Opaline and TizenTube (GPL-3.0) were read for facts only. Copy no code from the GPL projects. The SmartTube test fixtures are recorded YouTube responses with tracking data and an IP address: use them as layout reference only, never as No Slop fixtures.

## Sign-in (device code)

- **YouTube's own pair** (YouTube.js, SmartTube): `POST https://www.youtube.com/o/oauth2/device/code`, JSON `{client_id, scope, device_id, device_model: "ytlr::"}`. Poll `POST https://www.youtube.com/o/oauth2/token`, JSON `{client_id, client_secret, code: <device_code>, grant_type: "http://oauth.net/grant_type/device/1.0"}`. Refresh: same URL, `{client_id, client_secret, refresh_token, grant_type: "refresh_token"}`. No API key, cookie or special header.
- **Google's pair** (Smart Tube BDP): form posts to `https://oauth2.googleapis.com/device/code` and `/token`, with the same legacy grant type and a `code` field. Both pairs work for shipping apps today; whether a token from one refreshes on the other is untested.
- Device-code reply: `device_code, user_code, verification_url, expires_in, interval`. Poll errors: `authorization_pending` (keep polling), `slow_down` (wait longer), `access_denied` (stop), `expired_token` (new code). Read the JSON `error` field whatever the HTTP status (Google uses 428 for pending, 403 for slow_down and denied, 401 invalid_client, 400 invalid_grant).
- Scope used by SmartTube and YouTube.js: `http://gdata.youtube.com https://www.googleapis.com/auth/youtube-paid-content`. Others add `https://www.googleapis.com/auth/youtube`. Adding `accounts.reauth` makes the code request fail. The smallest working set is unknown.
- Client values: `GET https://www.youtube.com/tv` with a Cobalt user agent; the page has one `<script id="base-js">` (`/s/_/kabuki/_/js/.../m=base`, about 1.1 MB); a pattern on `clientId` finds the id and the secret next to it. Take the first match (SmartTube notes later matches give 401). Checked on 4 Nov 2026: one match, equal to the pairs Kodi and Smart Tube BDP bundle. Kodi once removed its pair as "revoked" (25 Sep 2024) and restored the same values (15 Nov 2024).
- Access tokens last about one hour (code comments; not measured). Projects keep the old refresh token after a refresh; keep a new one if a refresh returns it. A dead refresh token answers 400 or 401 with `invalid_grant` (or `invalid_client`, `unauthorized_client`).
- Revoke: Google documents `POST https://oauth2.googleapis.com/revoke` with `token=`; YouTube.js uses `https://www.youtube.com/o/oauth2/revoke`; neither Smart Tube app revokes. Manual route: Google Account, Security, third-party connections, "YouTube TV", Remove access.
- What the owner sees (second-hand): Google's page asks on behalf of "YouTube on TV"; the grant then shows as "YouTube TV". Reported verification URL: `https://www.google.com/device`. From Apple's CDN copy of the YouTube app's link file: `youtube.com/activate` and `google.com/device` stay in Safari, `youtube.com/qr/activate/<code>` would open the YouTube app.
- Same-phone sign-in on iOS (Smart Tube BDP): opens the verification URL plus `?user_code=` with `openURL`, shows the code, Copy Code and a countdown, polls again when the scene becomes active. ASWebAuthenticationSession does not fit (no redirect). Open issue 128: Google shows success but the app reports failure (cause unknown).
- These tokens work only with TV InnerTube contexts (WEB-family contexts answer HTTP 400 since November 2024) and not with the Data API.
- Brand accounts: `POST /youtubei/v1/account/accounts_list` with a TV context lists them; the `X-Goog-Pageid` header selects one. Without it the main identity is used.
- Attestation: SmartTube's "TV PoToken" (BotGuard, minted in a WebView) goes only on the full TV client's player request for streams. Browse, accounts_list, next, get_panel, feedback and the stats pings carry none in SmartTube's engine (code of 3 Nov 2026).

## Home (signed TV browse)

- `POST https://www.youtube.com/youtubei/v1/browse?prettyPrint=false` with `Authorization: Bearer <token>`, no `key`. Smart Tube BDP uses `youtubei.googleapis.com` instead; both hosts are in shipping use.
- Context `client`: `clientName: "TVHTML5"`, `clientVersion` 7.x (SmartTube `7.20260901.15.00`, Smart Tube BDP `7.20260707.07.00`, YouTube.js and Opaline `7.20260311.12.00`); a 5.x version breaks Home with HTTP 400. SmartTube also sends a Fire TV Cobalt user agent (it changes thumbnail sizes and menu content), `clientScreen: "WATCH"`, `tvAppInfo`, language, region, UTC offset and visitorData, plus `Referer: https://www.youtube.com/tv`. Opaline sends only Content-Type and Authorization with a small context. The smallest working set is unknown.
- `browseId`: `FEwhat_to_watch` (Smart Tube BDP, Opaline) or `default` (SmartTube since its November 2024 "empty home fix"). They look identical anonymously and inside continuation tokens.
- visitorData on signed calls is unsettled: SmartTube sends one read from /tv while its own comment warns visitor data can break history and suggestions on signed clients; Smart Tube BDP takes it from replies and some of its users see a non-personal Home. Never reuse No Slop's anonymous one.
- Layout (real signed-in captures of July 2025, paths still read by four apps in late 2026): `contents.tvBrowseRenderer.content.tvSurfaceContentRenderer.content.sectionListRenderer.contents[]` → `shelfRenderer` → `content.horizontalListRenderer.items[]` → `tileRenderer`. Other TV pages wrap this in `tvSecondaryNavRenderer` tabs. Shelf kind: `shelfRenderer.tvhtml5ShelfRendererType` (`..._GRID_XL`, `..._SHORTS`, `..._EDU`).
- Continuations: section level `sectionListRenderer.continuations[0].nextContinuationData.continuation` → `continuationContents.sectionListContinuation`; shelf level `horizontalListRenderer.continuations[0]...` → `horizontalListContinuation`. Send `{context, continuation}` with the same context. The feed is finite and ends with a Refresh button.
- Video tile (`contentType: TILE_CONTENT_TYPE_VIDEO`): id in `contentId` and `onSelectCommand.watchEndpoint.videoId`; title `metadata.tileMetadataRenderer.title.simpleText`; `lines[0]` channel name (not re-checked after mid-September 2026); `lines[1]` views, a bullet, the date (skip badge items such as 4K); thumbnail `header.tileHeaderRenderer.thumbnail.thumbnails`; duration in `thumbnailOverlays[].thumbnailOverlayTimeStatusRenderer.text` (its `style` is `LIVE` or `UPCOMING` for those); progress `thumbnailOverlayResumePlaybackRenderer.percentDurationWatched`. Text follows the request language: use structure, not text, for logic.
- Shorts: shelf type `..._SHORTS`, `TILE_CONTENT_TYPE_SHORTS` or `..._REEL`, style `TILE_STYLE_YTLR_SHORTS`, `reelWatchEndpoint`, overlay style `SHORTS`, `lockupViewModel` with `LOCKUP_CONTENT_TYPE_SHORT`. On 26 Oct to 3 Nov 2026 users reported Shorts reaching Home as ordinary-looking tiles without a duration.
- Not videos, never shown: `adSlotRenderer` inside shelves and directly in the section list (its inner `tileRenderer` looks real: never walk into it), `promoShelfRenderer`, shelves with `tvhtml5Metadata.hideLogo` (upsells), channel and topic tiles (`TILE_CONTENT_TYPE_CHANNEL`, `..._EDU`), `gridButtonRenderer`, `searchBarRenderer`, `feedNudgeRenderer`, paid or rental items (YPC badge; that badge also marks fundraisers). YouTube is adding `lockupViewModel` items to TV pages.
- Since about 15 to 23 Sep 2026 tiles no longer carry their long-press menu, channel id, handle or avatar; `onLongPressCommand.showEngagementPanelEndpoint` holds `identifier.tag` (seen: `PAcontext_menu`) and `globalConfiguration.params`, and one get_panel call per tile returns them.
- Signed-out reply (both ids, 4 Nov 2026): only `searchBarRenderer` and `feedNudgeRenderer`, `GFEEDBACK logged_in=0`. Tell signed-in from signed-out by `logged_in`, not by `maxAgeSeconds` (signed-in replies carry 1200, but so did one old signed-out capture).
- Volume: about 6 to 20 regular videos per page before filtering (the July 2025 first page had 5 unique ones). Repeats, already-watched videos and a sticky first tile are normal. Thin or nearly empty signed-in Homes were reported on 26 to 30 Oct 2026, cause unknown. Smart Tube BDP refreshes after 15 minutes in the background; no rate-limit reports for browse.

## Card menu and feedback

- `POST https://www.youtube.com/youtubei/v1/get_panel` with the TV context, `panelId` and `params` sent back unchanged, Bearer. Reply: `content.engagementPanelSectionListRenderer.content.listViewModel.listItems[]`: Play, Save to Watch later, Save to playlist, Go to channel (with the UC id), Not interested, Don't recommend channel; the header holds "Channel • @handle".
- Not interested: `rendererContext.commandContext.onTap.innertubeCommand.feedbackEndpoint.feedbackToken` (with a dismissal follow-up that can be ignored). Don't recommend channel: `openPopupAction`, then the confirm button's `feedbackEndpoint.feedbackToken`. Find both by structure; act only if exactly one of each is found.
- Send: `POST /youtubei/v1/feedback` with `{context, feedbackTokens: [token]}`, Bearer, no PoToken.
- Only Home and Shorts tiles have tokens. Up next, search and watch-page tiles have none, and Home has no undo token. Token lifetime is unknown. YouTube switched this data off and on three times between late July and mid-September 2026. SmartTube 32.54 (20 Sep) restored the actions this way; users still used them at the end of October.

## Reporting watches

- The tracking values in No Slop's anonymous playback reply are not credited. A separate signed player request is needed; only its `playbackTracking.videostatsPlaybackUrl` and `videostatsWatchtimeUrl` matter, and from their query: `ei`, `vm`, `of` (YouTube made vm and of mandatory in September 2025).
- SmartTube's current request (stable 32.68, 20 Oct 2026): `POST https://www.youtube.com/youtubei/v1/player`, legacy client `TVHTML5` `5.20260901` with an old Cobalt user agent, Bearer, `X-Goog-Visitor-Id`, `Referer: https://www.youtube.com/tv`; body with `context.client` (and visitorData), `playbackContext.contentPlaybackContext` (`html5Preference: HTML5_PREF_WANTS`, `signatureTimestamp`: the 5-digit web value, 20758 on 4 Nov 2026, which moves with each player build), `videoId`, `racyCheckOk`, `contentCheckOk`. No PoToken (the full 7.x TV player now needs one). Smart Tube BDP's 7.x signed player request returned "The page needs to be reloaded" on 22 Oct 2026. The googleapis host's TV player reply had no playbackTracking (July 2026).
- Pings, plain GETs, playback first: `https://www.youtube.com/api/stats/playback?ns=yt&ver=2&docid&len&cmt&cpn&ei&vm&of`, then `.../api/stats/watchtime?ns=yt&ver=2&docid&len&st&et&cmt&cpn&ei&vm&of`; `final=1` marks finished. Keep every item already in the base URL (yt-dlp: a missing `el=detailpage` makes it count as a Short). Bearer on pings (whether required is unknown). `cpn`: 16 characters from A-Z a-z 0-9 - _, new for each viewing, never reused across videos. Prefer www.youtube.com to s.youtube.com, which DNS blocklists catch.
- Timing: one tester says the first ping must follow the player request within seconds and an hour-old `ei` no longer credits. SmartTube reuses one ei, vm, of for the whole viewing (a new playback record after 30 minutes): about every 4 minutes while playing, on pause, seek and stop, and the final pair in the last 5%.
- Pings answer 200 whether credited or not. Only the history list shows success (signed TV browse of `FEhistory`; items are `tileRenderer`s in a `gridRenderer` or `tvSecondaryNavRenderer` tabs), seconds to about two minutes later. Watchtime pings also move the account's resume point.
- History: SmartTube's history broke in March, April to May and 3 Aug to 1 Sep 2026 (a TV signatureTimestamp format change), and its request changed again on 7 and 21 Sep. No crediting complaints from 23 Sep to 3 Nov 2026; one user found a SmartTube-watched video in YouTube history on 28 Sep. Smart Tube BDP's iOS attempt (PR 152, 26 Sep) is disputed: its author says it works, one user says it made things worse. Kodi credits through signed TV player requests too (fixed June 2026). No project replays reports later; YouTube probably dates an entry when the pings arrive.

## Up next (signed TV next)

- `POST https://www.youtube.com/youtubei/v1/next` with the TV context, `videoId`, Bearer. Layout: `contents.singleColumnWatchNextResults.pivot.sectionListRenderer.contents[]` (grid shelves of `tileRenderer`), `autoplay.autoplay.sets[]`, continuations in the pivot. An anonymous call on 4 Nov 2026 returned 30 suggestions, about a third related to the video. No 2026 evidence that the signed list is personal; signed captures of 2021 to 2024 had shelves such as "Watch it again" and "More recommended for you".

## Bot checks

- "Sign in to confirm you're not a bot" is a player reply status (`playabilityStatus.status: LOGIN_REQUIRED`). Every dated 2026 report concerns playback (Kodi 1494 from 20 Oct 2026 even after sign-in). None for browse, next, get_panel or feedback. The anonymous legacy TV player request from this Mac was bot-gated on 4 Nov 2026, so the reporting request must be signed.
